4. 值改變時觸發的互動(前端 onchange,IASCUS013.ascx:129-142)

一改變 ddlStkCusKind_IASCUS013,依序呼叫:

1. ChkNationality(v)(:1615):v 為 1(本國自然人)或 3(本國法人)時,國籍/居住國家自動預設為 TW。
2. ChkISISA(OKind, 國籍)(:1624):行業別為法人/非營利且國籍為美國相關代碼時,自動勾選「是否美國人士」為註冊公司。
3. ChkFCSettlement(OKind, v)(:1831):控制外幣交割資料列的顯示/唯讀(DVP 勾選時強制顯示且鎖定;法人+A 時有特殊分支)。
4. ChkInvestlimit(v)(:1888):v 為 A,或勾選 DVP 時,自動帶入「每日投資限額生效日/到期日」預設值,且投資限額欄位是否可編輯依新戶/改戶模式而定。
5. ChkKYCByStkCusKind(v)(:1849):v 為 3/4/6/7/A(法人類)時,KYC 問卷第 13、14 題設為唯讀(法人不用填)。同時 ddlStkCusKind_IASCUS013.Text 會寫入 KYC.GetPersonType,決定 KYC 子控制項要顯示自然人還是法人題組(IASCUS013.ascx.cs:444-446)。
6. v=='A' 時額外帶入 txtInvestLimitCDate/DDate 今日/次一營業日。

另外還有幾個不是掛在 onchange、但讀取這個欄位值的邏輯:

- SetGIINCusKind()(:562-573):v 為 3/4/6/7 時,GIIN、CusKind(FATCA客戶類別)欄位才可編輯,否則清空並鎖定。
- IsCorp()(:2548-2558):判斷是否為法人負責人須填國籍的規則之一是 v=='4' 或 'A',或(行業別=40 且 v=='C' 且 OBU='Y')——這裡出現了不在下拉選單產生邏輯裡的 C。
- CheckPaperFlag()(:4161-4169,對應提示文字在 :1331):v 為 5/6/7/0/A 時,密碼條作業別只能選「紙本」,不能選網路發送。這裡出現了同樣不在下拉選單產生邏輯裡的 0。

5. 伺服器端的強制覆蓋(不是使用者選的)

IASCUS013_DAO.cs:541-554(複製舊資料/GetLastestStkDataList 類方法):若查到的既有帳號 isEMP(內部人 RID 代碼)不為空,不論原本客戶性質是什麼,伺服器端強制把 CusKind 和 StkCusKind 都覆蓋成 8(RID='0' → CusKind=2;RID='1'或'3' → CusKind=3,兩者 StkCusKind 皆覆蓋為8)。這與前端 rdoCusKind_IASCUS013 改變時彈出的「客戶非內部人,請確認客戶性質是否為員工或員工眷屬」confirm 對話框(:79-89)是同一套「內部人員工」防呆機制的一體兩面。

6. ⚠️ 需要你確認/待釐清的兩點

1. 代碼 0(複受託券商)與 C 從未出現在 GetSubContractType 的下拉選單產生邏輯裡(我搜過整支 DAO 的 switch,50/60/40/41/4041/9999 都不會回傳 0 或 C),但 013 畫面裡卻有程式邏輯在檢查這兩個值(CheckPaperFlag、IsCorp)。也就是說,這兩個值目前只可能透過既有舊資料(Modify 模式讀進來的既有欄位值)出現,使用者在 013 新增流程中無法透過畫面主動選到。這是否為既知的「舊資料相容」設計,還是有其他我沒找到的來源,需要你確認。
2. C 的正式業務名稱我沒有把握。唯一找到的具體線索是 IASCUS016.ascx.cs:210-218(IASCUS016 = OSU 模組,線上開戶轉入 CUSDATA 時)硬編碼 pdata.StkCusKind = "C",同時設定 IndustryType="60"(個人)、IsOBU="Y"——研判是「OBU 個人線上開戶」相關的客戶性質,但 Descript 文字本身沒在程式碼裡找到,需要你確認正式名稱。

7. 跨模組關聯提醒(針對 013 重構)

- 這個欄位跟 IASCUS012(證券開戶)完全沒有共用——我在 IASCUS012.ascx 搜「客戶性質」和 StkCusKind 都沒有結果,和一般 012/013 常共用欄位的模式不同,算是一個例外。
- 但跟 IASCUS016(OSU)有實質耦合,而且是意料之外的方向——IASCUS016.ascx.cs:511 直接呼叫 IASCUS013_DAO.GetSubContractType(...) 取得它自己 DVP 子選單的選項,代表 IASCUS016 依賴 IASCUS013 的 DAO 類別。重構 013 時如果搬動或改掉 IASCUS013_DAO.GetSubContractType 的簽章或邏輯,會直接影響到 016,要一併評估。
- 另外 App_Code/Service/SUB/DAO/SubCusDataDAO.cs:813 也有讀取 StkCusKind(判斷是否為 1/2/8 自然人),SUB 這個模組代碼目前還沒跟你確認過業務意涵,如果它跟複委託開戶有資料轉出/轉入關係,也建議一併納入重構影響範圍評估。
